# Environment Variables

Multichamber reads these environment variables at startup. For startup services, `multichamber startup enable` snapshots the current environment by default, so rerun it after changing variables you want the service to use. Variables Multichamber itself set in the shell you run it from, such as the desktop app's terminal or an agent's shell, stay out of the service; your own exports carry over from there too, unless you re-export a name Multichamber already set in that shell, which a regular terminal avoids.

## Variables for OpenCode, Git and the terminal

To give OpenCode, Git, the terminal and [project actions](/project-actions/) variables of your own, such as an API token or a database address, add them in **Settings → General → Environment variables** instead of exporting them before Multichamber starts. Values stay on the machine that runs Multichamber, in `environment.json` in the data directory, readable only by your user. Settings never shows a value again: you can replace or remove it, not read it back.

- OpenCode gets them when it starts, so restart it after a change. Settings offers the button.
- Variables you set with `opencode service set env` reach OpenCode too. The ones from Settings win.
- Git, the terminal and project actions get them on their next run.
- Variables Multichamber sets for OpenCode itself, like its password and config, win over yours.

A project can add its own variables, or a command such as `direnv export json` that prints them, in **Settings → Projects**. See [Projects](/projects/#project-environment).

The variables don't reach an OpenCode server you started yourself, and the VS Code extension has no such setting. Everything below is read by Multichamber itself at startup.

## Multichamber server

### `MULTICHAMBER_HOST`

Bind address for the Multichamber web server. Use `0.0.0.0` to allow access from other machines.

### `MULTICHAMBER_LAN_URL`

The address other devices on your network use to reach Multichamber, such as `http://192.168.1.20:3000`. Pairing links and QR codes offer it instead of the address Multichamber detects itself. Set it when that guess is wrong, for example in Docker, where Multichamber only sees the container's internal address.

### `MULTICHAMBER_UI_PASSWORD`

Password for the browser UI. Use this when binding outside localhost, using tunnels, or running behind a reverse proxy.

### `MULTICHAMBER_UI_SESSION_TTL_HOURS`

How long a browser sign-in lasts, in hours, when "trust this device" is off. The default is `12`.

### `MULTICHAMBER_UI_TRUSTED_SESSION_TTL_DAYS`

How long a sign-in lasts, in days, on a device you chose to trust. The default is `7`.

### `MULTICHAMBER_API_ONLY`

Starts Multichamber in headless mode when set to `true` or `1`. API routes stay available for desktop and mobile clients, but the browser UI is not served.

### `MULTICHAMBER_FRAME_ANCESTORS`

Origins allowed to show Multichamber inside a frame on their own page, separated by spaces, for example `https://dash.example.com`. `*` allows any site. By default only Multichamber itself and its desktop and mobile apps may frame it, which keeps other sites from overlaying its buttons.

### `MULTICHAMBER_DATA_DIR`

Overrides the Multichamber data directory. The default is `~/.config/openchamber`.

Everything Multichamber stores lives under this directory: settings, auth, project configs, themes, plans, and speech models. An instance that used a custom directory before version 1.23 gets its `projects`, `themes`, and `speech-models` folders copied from `~/.config/openchamber` on the first start; the originals stay in place and nothing is merged.

### `MULTICHAMBER_CHATS_DIR`

Moves the managed chat directories that Multichamber creates for chats without a project. The default is `~/.config/openchamber/chats`. Set it to a directory the OpenCode server can read when Multichamber and OpenCode run as different users. Existing chats are not moved.

### `MULTICHAMBER_COMPRESS_API`

Controls API response compression. Use `true` or `1` to force it on, `false` or `0` to force it off.

### `MULTICHAMBER_SKIP_API_COMPRESSION`

Disables API response compression when set to `true` or `1`. This takes precedence over `MULTICHAMBER_COMPRESS_API`.

### `MULTICHAMBER_VERBOSE_REQUEST_LOGS`

Enables verbose HTTP request logs when set to `true` or `1`.

### `MULTICHAMBER_UPDATE_API_URL`

Overrides the update-check API endpoint. Most users should leave this unset.

### `MULTICHAMBER_PACKAGE_MANAGER`

Forces the package manager used by update operations when auto-detection is wrong.

## Proxy

### `HTTP_PROXY`, `HTTPS_PROXY`, `NO_PROXY`

Sends Multichamber's own outgoing requests, such as usage limits and skill catalogs, through a proxy. Lowercase names work too. Hosts in `NO_PROXY` connect directly, and `localhost`, `127.0.0.1` and `::1` always do, so sign-in callbacks and the local OpenCode server keep working.

## OpenCode server

### `OPENCODE_HOST`

Connects Multichamber to an existing OpenCode server. The value must be an `http` or `https` origin with an explicit port and no path, query, or hash. `OPENCODE_HOST` takes precedence over `OPENCODE_PORT`.

### `OPENCODE_PORT`

Sets the OpenCode server port. With managed OpenCode this requests the managed port; with `OPENCODE_SKIP_START=true` it connects to an external server on that port.

### `OPENCODE_SKIP_START`

Prevents Multichamber from starting its own OpenCode server when set to `true`.

### `MULTICHAMBER_OPENCODE_HOSTNAME`

Bind hostname for the OpenCode server managed by Multichamber. The default is `127.0.0.1`.

### `OPENCODE_BINARY`

Path to the `opencode` executable Multichamber should run.

### `OPENCODE_CONFIG`

Path to a specific OpenCode config file.

### `OPENCODE_CONFIG_DIR`

Path to a specific OpenCode config directory for agents, skills, snippets, and config discovery.

### `OPENCODE_DATA_DIR`

Custom data directory for the managed OpenCode server.

### `OPENCODE_WSL_DISTRO`

Selects the WSL distro used for OpenCode integration on Windows.

### `MULTICHAMBER_OPENCODE_WSL_DISTRO`

Multichamber-specific alias for selecting the WSL distro. `OPENCODE_WSL_DISTRO` takes precedence when both are set.

### `OPENCODE_JWT_SECRET`

Secret used to sign UI authentication tokens. Use a long random value for persistent service deployments.

## Terminal and Git

### `MULTICHAMBER_TERMINAL_SHELL`

Shell executable used for Multichamber terminal sessions.

### `MULTICHAMBER_GIT_BINARY`

Git executable used by Multichamber Git features.

### `GIT_BINARY`

Alternative Git executable override. Prefer `MULTICHAMBER_GIT_BINARY` for Multichamber-specific configuration.

### `MULTICHAMBER_GIT_READ_CACHE_TTL_MS`

Time-to-live, in milliseconds, for cached Git-backed file reads. Set `0` to disable this cache while debugging.

## Voice and tunnels

### `OPENAI_API_KEY`

API key Multichamber voice features use when they call OpenAI itself. It is never sent to a custom OpenAI-compatible server: give that server its own key in Settings.

### `MULTICHAMBER_ALLOW_REMOTE_OPENAI_COMPAT_URLS`

Allows remote OpenAI-compatible base URLs for voice features when set to `true` or `1`.

### `NGROK_AUTHTOKEN`

ngrok auth token used by Multichamber tunnel commands. You can also configure ngrok with `ngrok config add-authtoken <token>`.

## Runtime helpers

### `BUN_BINARY`

Bun executable Multichamber should use when spawning daemon processes.

### `BUN_INSTALL`

Bun installation root. Multichamber uses it to find `bin/bun` for daemon startup and updates.

### `VITE_OPENCODE_URL`

Build-time API base URL for the Vite-built web app. Most users should not set it for normal CLI or desktop usage.
